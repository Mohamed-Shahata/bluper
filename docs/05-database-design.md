# 1. Purpose

This document defines the logical database design of Bluper.

Its purpose is to describe how application data is organized, stored, and related without depending on any specific ORM implementation.

The database should support the complete AI workflow while remaining maintainable, scalable, and easy to extend.

References:

- ADR-001
- ADR-003

---

# 2. Database Philosophy

The database is designed around business entities rather than AI prompts.

Every table should represent a meaningful business concept.

The design prioritizes:

- Normalization
- Clear relationships
- Data consistency
- Extensibility
- Maintainability

The database should remain independent of AI providers.

---

# 3. Database Technology

Version 1 uses:

- PostgreSQL
- Relational Database Model
- ACID Transactions
- UUID Primary Keys

The implementation layer (Prisma ORM) is outside the scope of this document.

---

# 4. Design Principles

The database should follow the principles below.

## Single Source of Truth

Every business entity should exist only once.

---

## Normalization

Data duplication should be minimized whenever practical.

---

## Explicit Relationships

Relationships between entities must be represented through foreign keys.

---

## Immutable Historical Data

Generated blueprints should remain immutable after completion.

New versions should create new records instead of modifying existing ones.

---

## Separation of Concerns

Business data, AI workflow data, and generated outputs should remain logically separated.

# 6. Core Entities

The system consists of the following primary entities.

## User

Represents an authenticated user.

---

## Project

Represents a software project created by a user.

---

## ProjectDescription

Stores the original project idea provided by the user.

---

## Requirement

Stores finalized functional and non-functional requirements.

---

## Question

Represents clarification questions generated by the system.

---

## QuestionAnswer

Stores user answers to generated questions.

---

## ExecutionContext

Represents the complete structured context shared between AI Agents.

---

## WorkflowExecution

Represents a single AI workflow execution.

---

## AgentExecution

Stores execution details for each AI Agent.

---

## Blueprint

Represents the final Software Blueprint.

---

## BlueprintSection

Stores individual blueprint sections.

Examples:

- Requirements
- Architecture
- Database Design
- API Design
- Security
- Documentation

---

## Recommendation

Stores AI-generated recommendations such as:

- Technology Stack
- Architecture Style
- Design Patterns

# 8. Data Integrity Rules

The following integrity rules must always be enforced.

DB-001

Every Project belongs to exactly one User.

---

DB-002

Every Workflow Execution belongs to one Project.

---

DB-003

Every Agent Execution belongs to one Workflow Execution.

---

DB-004

Every Blueprint belongs to one Workflow Execution.

---

DB-005

Blueprint Sections cannot exist without a Blueprint.

---

DB-006

Question Answers cannot exist without a Question.

---

DB-007

Execution Context must exist before AI Agent execution begins.

---

DB-008

Completed Blueprints are immutable.

# 9. Indexing Strategy

Indexes should be created for frequently queried fields.

Recommended indexes include:

- userId
- projectId
- workflowExecutionId
- blueprintId
- createdAt
- status

Composite indexes may be added when justified by query patterns.

---

# 10. Soft Delete Strategy

Business entities may support soft deletion.

Soft-deleted records should not appear in normal application queries.

Blueprint history should never be deleted automatically.

---

# 11. Auditing Strategy

The system should maintain basic auditing information.

Standard fields include:

- createdAt
- updatedAt

Future versions may include:

- createdBy
- updatedBy
- version
- changeHistory

---

# 12. Future Scalability

The database should support future features including:

- Blueprint Versioning
- Multiple AI Providers
- Team Workspaces
- Shared Projects
- Export History
- AI Usage Analytics
- Prompt Templates
- Organization Accounts

The current schema should allow these features to be added with minimal structural changes.
