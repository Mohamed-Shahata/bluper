# 1. Context

Bluper executes multiple AI Agents sequentially to generate a complete Software Blueprint.

Each agent depends on information generated by previous agents.

Examples include:

- Project Summary
- User Answers
- Requirements
- Technology Recommendation
- Architecture Decisions
- Module Structure

Without a shared source of truth, each agent would need to reconstruct project knowledge independently.

---

# 2. Problem Statement

Passing only the previous agent's output creates several issues:

- Information loss
- Duplicate reasoning
- Inconsistent engineering decisions
- Larger prompts
- Difficult retry execution
- Increased token usage

The workflow requires a centralized execution state that all agents can access.

---

# 3. Decision

Bluper will maintain a **Shared Execution Context** throughout the entire workflow.

The Shared Execution Context is a structured JSON object managed exclusively by the Workflow Orchestrator.

Every agent receives the current Execution Context as read-only input.

Only the Workflow Orchestrator is responsible for updating the shared context after validating an agent's output.

Agents must never modify the Execution Context directly.

---

# 4. Execution Context Structure

The Execution Context may contain:

- Execution metadata
- Project information
- User answers
- Approved requirements
- Recommended technologies
- Architecture decisions
- Module definitions
- Database model
- API specification
- Security strategy
- Generated documentation
- Validation status
- Retry metadata

The exact structure may evolve without changing the workflow architecture.

---

# 5. Rationale

A shared execution state provides several advantages:

- Single source of truth
- Consistent engineering decisions
- Lower prompt size
- Reduced token consumption
- Easier retries
- Easier debugging
- Better observability
- Simpler agent design

Each agent focuses only on producing its own output.

The Workflow Orchestrator is responsible for state management.

---

# 6. Alternatives Considered

## Agent-to-Agent State Passing

Advantages

- Simple implementation.

Disadvantages

- Information fragmentation.
- Difficult retries.
- Growing prompt sizes.
- Strong coupling.

Decision

Rejected.

---

## Independent Agent Memory

Advantages

- Independent reasoning.

Disadvantages

- Duplicate analysis.
- Higher cost.
- Inconsistent decisions.
- Poor traceability.

Decision

Rejected.

---

## External Persistent Storage

Advantages

- Durable workflow state.
- Recovery after failures.

Disadvantages

- Additional infrastructure.
- More implementation complexity.
- Unnecessary for current workflow.

Decision

Deferred.

Persistent execution storage may be introduced in a future version if required.

---

# 7. Consequences

Positive

- Consistent engineering decisions.
- Lower token usage.
- Easier workflow management.
- Predictable execution.
- Better debugging.
- Simpler agent implementation.

Negative

- Execution Context becomes a critical dependency.
- Requires careful schema management.
- Context validation becomes the responsibility of the Workflow Orchestrator.

---

# 8. Trade-offs

| Benefit                | Cost                                    |
| ---------------------- | --------------------------------------- |
| Single source of truth | Centralized state management            |
| Smaller prompts        | Context schema maintenance              |
| Better consistency     | Additional orchestration responsibility |
| Easier retries         | Versioning of shared context            |

The benefits significantly outweigh the additional complexity.
